# PR Title and Description

Write for a reviewer who has not seen this session, the plan, the ticket thread or the worktree. They know the codebase in general, but not what you have been doing. They should understand the change in under a minute.

## Context

- Branch: !`git branch --show-current`
- Commits: !`git log origin/HEAD..HEAD --oneline 2>/dev/null || git log --oneline -10`
- Changed files: !`git diff origin/HEAD..HEAD --stat 2>/dev/null || git diff --stat HEAD~5`
- Current PR: !`gh pr view $ARGUMENTS --json number,title,body,url 2>/dev/null || echo "no PR yet"`
- Repo PR template: !`ls .github/pull_request_template.md .github/PULL_REQUEST_TEMPLATE.md .github/PULL_REQUEST_TEMPLATE/ docs/pull_request_template.md pull_request_template.md 2>/dev/null || echo "none"`

## Voice

Write it as me, following my writing style (`~/.claude/rules/writing-style.md`): lead with the point, short and focused, plain words, "so" to connect thoughts, no em-dashes, no AI slop. It should read like I wrote it by hand.

## Title

- Conventional commit style, under 72 characters: `fix(auth): keep users signed in after a token refresh`
- Describe the effect, not the implementation. `fix(search): show results for queries with accents`, not `fix: normalize input in useSearchQuery`
- No ticket IDs, phase numbers or branch names unless the repo's convention asks for them

## Description

If the repo has a PR template (see Context, and check `CONTRIBUTING.md` or the repo's agent instructions for one), use it: keep its headings and checkboxes, fill each section following the rules below, and write "N/A" in required sections that don't apply instead of deleting them. If there are several templates, pick the one that fits the change. When there's no template, use this:

```markdown
<1-3 sentences: what changes for the user or the system, and why>

<Optional: bullets for anything the diff doesn't make obvious>

## Testing

<How a reviewer can check it, or what you checked. Skip if trivial>
```

- Lead with the outcome. The first sentence should be enough to approve the idea
- Only list a change when a reviewer would miss it or wonder why. Don't walk through the diff file by file
- Call out what needs attention: risky parts, migrations, breaking changes, follow-ups left out on purpose
- Link the issue at the end (`Closes #12`, or the Linear URL)
- Keep it as short as the change allows. A one-line fix gets a one-line description, and outside a repo template, empty sections get dropped

## Remove implicit knowledge

Everything in the description must make sense to someone who only has the PR. Cut or explain:

- References to the session: "as discussed", "per the plan", "option B", "step 3", "the approach we agreed on", "now", "the new way"
- Names that only exist in your head or scratch files: helper nicknames, planning.md headings, worktree names
- Earlier attempts and dead ends, unless they explain why the obvious approach wasn't taken (then one sentence)
- "Fixes the issue" without saying what the issue was

## Remove jargon

- Use the product's or codebase's own terms, not ones you invented while working
- Spell out abbreviations the first time unless they're universal (`API`, `URL`, `CI`)
- Name code identifiers in backticks only when the reviewer needs to find them
- Prefer plain words: "runs once on start" over "idempotent bootstrap hook"

## Remove padding

- No "This PR...", "In this change we...", "Overall, this improves..."
- No restating the title in the first sentence
- No lists of files touched, no "updated tests accordingly", no "ran lint"
- No marketing words: robust, seamless, comprehensive, enhanced, streamlined
- Don't mention the code was generated by Claude
- Avoid em-dashes; use commas or parentheses

## Example

Before:

```markdown
## Summary
This PR implements Option B from the plan, refactoring the TokenManager flow to use the new refresh strategy we discussed. This makes auth handling more robust and seamless.

## Changes
- Updated `token-manager.ts` to use `refreshV2`
- Updated `auth-context.tsx` accordingly
- Updated tests
- Ran lint and typecheck

## Test Plan
Tests pass.
```

After:

```markdown
Users were signed out when two requests refreshed the access token at the same time, because the second refresh invalidated the first. Concurrent requests now wait for a single shared refresh.

- `token-manager.ts` keeps the in-flight refresh promise and reuses it until it settles

## Testing

Open two tabs, let the token expire, then reload both. Both stay signed in.

Closes #142
```

## Process

1. Read the diff (`gh pr diff`, or `git diff origin/HEAD..HEAD`) and the linked issue. Base the description on what the code does, not on what this session talked about
2. Draft the title and description
3. Re-read the draft as the reviewer: strike every sentence that needs this session to make sense, or that adds nothing beyond the diff
4. Show me the draft (and the current one if rewriting)
5. Apply after I confirm: `gh pr edit <number> --title "..." --body-file -`, or hand it back to the `pr` skill when opening a new PR
